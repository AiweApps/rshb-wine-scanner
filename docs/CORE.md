# Ядро распознавания для Linux CPU

`wine_scanner_core` запускает распознаватель в контейнере Linux без Mac, MPS и Apple Vision.
Код ядра и исполняемый код распознавателя лежат в этом репозитории. Веса, галерея, каталог и профили
поставляются отдельным пакетом активов. Пакет подключается только для чтения.

## Из чего состоит

| Часть | Где | Что проверяется при старте |
|---|---|---|
| `recognizer/` | Git | Байтовые копии serving-кода исходного проекта (`rshb_vine/`, `scripts/`) и журнал `SOURCES.json`: SHA-256, исходный SHA, происхождение. Посторонние файлы запрещены |
| `wine_scanner_core/` | Git | Новый код: пак, квитанция, Linux-адаптер, HTTP. Его SHA входят в дескриптор |
| Пакет активов | вне Git | `manifest.json` закреплён по SHA-256. Каждый файл `tree/…` сверяется по SHA и размеру. Неучтённые файлы запрещены |
| `docker/core.Dockerfile` | Git | Образ со всеми зависимостями. Их точные версии взяты `--no-deps` из `docker/core-requirements.txt` |

Файлы пакета лежат по тем же относительным путям, что в исходном проекте: `config/`, `data/`, `models/`, `runs/`.
Вендоренный код проверяет свои пины по этим путям. Compose монтирует четыре каталога в `/srv/core` поверх `recognizer/`.

## Что выполняется

Вендоренный выпуск — родитель `3c8c2da4` / runtime `08378488`. До его сборки ядро выполняет следующие замены,
и каждая записывается в `/v1/core`:

- MPS заменяется на CPU в пяти конструкторах моделей;
- оба слота Apple Vision заменяются на PP-OCRv6 medium (det+rec, `v6_medium_native`). Бинарник Vision не запускается,
  любая попытка запуска падает;
- колёса torch/torchvision с меткой `+cpu` сообщают версию без метки только двум закреплённым version guard;
- Paddle работает в 2 потока: на Linux/arm64 при 4 потоках PP-OCRv6 падает.

Веса, пороги, галерея и ранжирование не меняются. После загрузки ядро проверяет:

- контрольные суммы родителя совпадают;
- в графе нет обращений к Vision;
- все тензоры на CPU.

## Проверки происхождения вне поставки

При загрузке вендоренный выпуск проверяет:

- энкодер B4343 получен допущенной цепочкой обучения;
- добавленные эталоны не входят в защищённые наборы оценки;
- источники конфликтов эталонов не изменились.

Эти проверки читают обучающий корпус, составы защищённых разбиений и журналы оценки. Эти данные в пакет не входят:
91 файл. Экспортёр выпуска выполнил исходные проверки на этих данных и записал квитанцию `provenance` в манифест пакета.

- Три функции заменяются записанным результатом, только если аргументы совпали: `reindex.encoder_arm`,
  `admission.protected` (результат обязан быть `{}`) и `guard.source_checks` (все проверки `ok`, покрыт весь config).
  При другом вызове ядро падает.
- `encoder_arm` при восстановлении заново сверяет файлы энкодера и пересчитывает `encoder_id`
  по `models.py` и препроцессингу.
- Для изъятых файлов, которые код только хеширует, известный SHA выдаётся лишь записанным вызывающим функциям.
  Сам файл при этом должен отсутствовать. Остальные `sha256`, `read_json` и `verify` работают как обычно.
- Активные проверки остаются живыми: identity добавленных SKU, фильтры `ReferenceConflicts`, SHA галереи и весов.

Поле `encoder_dir` записанного arm хранит путь сборки из gallery receipt: он нужен для сравнения байт в байт.
Модель загружается из фактического пути в контейнере. Этот путь есть только в пакете активов, не в Git.

## Дескриптор

`python -m wine_scanner_core describe` вычисляет дескриптор без загрузки моделей. В него входят:

- SHA манифеста пакета;
- журнал исходников;
- код ядра;
- квитанция;
- V6-дескриптор;
- параметры исполнения (Linux, CPU, OCR, потоки).

Родитель указан отдельно, как происхождение. Дескриптор возвращает `/health/ready`.
В каждом ответе он стоит в `target_contract.profile_checksum`, профиль родителя — в `core_parent_profile_checksum`.
Пакет веб-активов gateway привязывается к нему через `tools/bind_web_assets.py`. Так все три проверки gateway
совпадают с тем, что реально работает.

## Запуск

`describe`, `verify` и `preflight` модели не загружают. `preflight` сверяет каждый файл и затем прогоняет цепочку профиля
выпуска и три guard-замены. На 2 CPU это занимает около 2,5 минут. `serve` сначала делает `verify`, затем собирает
распознаватель.

```bash
# .env: WINE_SCANNER_CORE_ASSETS_HOST_DIR, WINE_SCANNER_CORE_ASSETS_SHA256, WINE_SCANNER_CORE_EXPECTED,
#       WINE_SCANNER_LINUX_ASSETS_HOST_DIR, WINE_SCANNER_LINUX_ASSETS_SHA256 и блок gateway (см. README)
docker compose --profile linux build core gateway-linux
docker compose --profile linux run --rm --no-deps core describe   # дескриптор без загрузки моделей
docker compose --profile linux up -d core gateway-linux
curl --fail http://127.0.0.1:8375/health/ready   # проверка пакета и загрузка, около 3,5 мин в проверенном запуске
curl --fail http://127.0.0.1:8387/health/ready   # шлюз; интерфейс — http://127.0.0.1:8387/
```

Используется обычная bridge-сеть Docker, порты опубликованы только на 127.0.0.1.
На проверенном Docker Desktop `internal:true` делает опубликованные порты недоступными,
поэтому сетевую изоляцию от интернета эта конфигурация не обещает. Модели и OCR
читают локальные активы; HF/Paddle настроены на offline-работу.
`gateway-linux` разделяет сетевое пространство ядра и обращается к нему по `127.0.0.1:8375`. Код gateway не меняется.
Профиль по умолчанию (`gateway` → распознаватель на Mac `:8175`) остаётся прежним.
Ресурсы ядра: 2 CPU, лимит 12 ГБ. В smoke пиковый RSS был около 3,1 ГБ.

## Границы

- Закрытие пакета собрано так:
  - трассировка загрузки и 5 открытых запросов (3 вина, ROI, не вино);
  - статическое закрытие импортов этого кода (+12 модулей);
  - эталонные изображения галереи из инвентаря выпуска.

  Другие условные ветки могут прочитать файл, которого нет в пакете. Тогда запрос завершится ошибкой, подмены не будет.
- В пакете остаются протоколы и агрегированные отчёты прежних опытов: их читают конструкторы вендоренного кода.
  Там же лежат семь исторических `.py` (`config/dispatch-archive/…`, `runs/…`). Выпуск только хеширует их для пинов
  и не импортирует. Serving-код — только `recognizer/`.
- Ядро проверяет, что пакет активов выпущен для того же журнала исходников (`source_ledger`).
  Корпуса и составов защищённых наборов в пакете нет.
- Вендоренный код — переходная форма: многослойный выпуск перенесён без переписывания, чтобы сохранить поведение.
- OCR V6 на Linux побайтно не совпадает с Mac V6 (OpenCV/потоки). Smoke подтверждает работоспособность, это не новая оценка точности.
  Уверенность не откалибрована.

## Проверенный запуск · 28 сентября 2026

Образ `f6e1e13b`, вариант исполнения `20fcadedd9d3`, Linux/ARM64, 2 CPU / 12 ГБ.
Контейнер содержал код из этого репозитория и подключал только отдельные пакеты
активов; исходный рабочий каталог проекта не монтировался. 302 исходника и 4405 файлов активов
проверены по SHA; объём активов 5,28 ГБ, веса вне Git и образа.

Выполнены 10 HTTP-запросов: три известных открытых фото вина, повтор одного с ROI
и фото без вина — напрямую к ядру и через gateway. Все 5 сценариев прошли обоими
путями: три вина и ROI распознаны правильно, negative вернул 0 целей. Первые ответы,
Top5 и рамки совпали с исходным Linux-прогоном; ошибок OCR/Vision нет.

Прямой запрос: 6,28/8,44/10,02 с, ROI 6,33 с, негатив 19,22 с. Через gateway:
6,23/8,68/9,26 с, ROI 6,37 с, негатив 20,20 с. Собственная загрузка runtime — 86,7 с
плюс проверка пакета. Это smoke на трёх известных товарах, не новая независимая
оценка точности и не нагрузочный тест. SLA 10 с не подтверждён; x86_64 не проверен.
